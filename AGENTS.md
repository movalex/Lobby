# Draftroom repository rules

This repository implements `docs/Miro_Clone_Build_Plan.md` (product + architecture baseline) using the milestone sequence in `docs/Cursor_Start_Here.md`. Read `docs/PROGRESS.md` before making changes and update it when a milestone or workflow finishes. Verified engine facts live in `docs/research/excalidraw/` (current canvas engine and sync) and `docs/FEASIBILITY.md`; `docs/research/SYNTHESIS.md` is history for the tldraw era.

## Working rules

- Work from the queued milestones and their acceptance gates. Independent tasks may run in parallel only with explicit file ownership and shared contracts; serialize changes to shared schemas, dependency versions and the lockfile.
- Keep code deployable in small increments. Inspect installed exports (`node_modules/@excalidraw/**/*.d.ts` and `dist/dev`) before relying on an API name — Lobby pins an Excalidraw nightly (`0.18.0-1118751`) that is newer than most model training data. Pin all five `@excalidraw/*` packages to the same exact version; bump them only in a dedicated PR that runs the engine probe suite (`apps/web/test/engine-probe`) and the full gate. Pin exact dependency versions (via the pnpm `catalog:`) and record migrations.
- Run meaningful targeted checks, review changes, and record evidence. Do not broaden scope or upgrade unrelated dependencies. Do not provision paid resources, contact vendors, or publish an unreviewed deployment.
- Do not present a demo, mock, or unverified benchmark as a finished feature. Do not mark unrun checks as passing.

## Architecture invariants

- Canvas state has one authority: Lobby's element sync server (`apps/sync` `ElementRoom`). Exactly one room owner per board, one SQLite database per board, and only the sync process writes a board file (including conversion). Acks are sent only after COMMIT.
- Until `drop-legacy`, the new build never writes, trims or alters the tldraw tables or `dr_deleted_*` in a board file; it copies from them (`lb_source`, `lb_deleted`). The bridge release never writes `lb_*`.
- Do not add a second sync or merge layer: no Yjs, Liveblocks, Excalidraw collab/Firebase, and no `reconcileElements` as a merge rule. Do not add a whole-board overwrite save loop or debounce board JSON into a last-writer-wins endpoint.
- Apply every server or remote change to the editor with `CaptureUpdateAction.NEVER`, only through the sync adapter. A client that only receives changes must push nothing: clients re-key only their own unacknowledged elements, image `status` is local-only, and every new echo source gets a rule and a test.
- Never put base64, `data:`, `blob:` or signed/expiring URLs in elements, `customData`, `link` or board settings. Elements store stable Lobby ids (`fileId` = a version id). The editor's files map is runtime-only, filled by Lobby's loader.
- Element schemas, field groups, `customData` key classes, cross-element invariants, limits, the wire protocol and migrations live in `packages/canvas-schema` and are used by client, server, converter and archive import. Every element write is validated server-side, per op, including references between elements and identity-bearing `customData`. A test fails when an element field belongs to no field group. Test reconnects, process restarts, stale clients and concurrent modifications when those paths change.
- A tab of the previous build stays open for days and drops a whole server frame it cannot parse. So every frame reaches a client in its contracts revision's form (the connect URL names the revision; the room sends every frame through canvas-schema's `frameForReader` at its one send point, `Session.send`), and a write from an older revision keeps the fields it cannot know (`lobbyWriteOf`). A `CONTRACTS_REV` bump freezes the deployed build's schemas as a fixture and proves both against them and against that real build in a browser (docs/EXCALIDRAW-CONTRACTS.md §0b); a shim around the current client is no proof.
- Undo is Lobby's field-level stack: entries are recorded against the previous local state, server fixes fold into their entry and never create a step, it changes only fields, `customData` keys and group ids whose current value is still what the entry left, and it never revives an element someone else deleted.
- Text in an element is edited only under a server-granted lease; only the holder writes its words, its layout and its container's fit (for a free text, its own position while typing). Bound arrow endpoints are always server-derived: no client pushes an arrow change that only moved its bound endpoints (decided by comparing the arrow's user-set geometry within the stated tolerance in `limits.ts`, never by guessing the cause and never bit-exactly), an arrow's or line's whole geometry (`x`, `y`, `points`, `width`, `height`, `angle`, and `fixedSegments`, `startIsSpecial`, `endIsSpecial` and `elbowed`, or `polygon`) is always written together as one unit and rebased only with Excalidraw's own `movePoints`, and the server re-snaps the bound ends (and moves the arrows' labels) in the same commit as any write that changes a target's position, size or angle, or the arrow's own geometry. No text editor is ever writable unless its element is that of a lease this tab holds, whatever state Lobby's lease client is in. Every path that opens Excalidraw's text editor is intercepted or caught by the guard in `apps/web/src/canvas/input/`; a new path found after a bump must be added before the bump merges.
- Only `apps/web/src/canvas/**` and `packages/canvas-schema/src/engine/**` may import `@excalidraw/*`. Features use `CanvasPort` and the registries.
- Keys reach Excalidraw only through the allowlist in `apps/web/src/canvas/input/`; inside the text editor, Ctrl/Cmd/Alt chords are an allowlist too, and AltGr/Option text input still types. Every `canvasActions` flag stays off; read-only roles use the `interaction` config, and their tool is set through `appState`. A File System Access picker call counts as a download in every test.
- Embeddables and iframes stay disabled (`validateEmbeddable` returns false; the server refuses those types) unless a reviewed change adds a Lobby-only allowlist.
- No request leaves Lobby's own origins and the auth provider's: self-host Excalidraw's fonts without Liberation Sans, with a same-origin font fallback and a 404 (not `index.html`) for missing files under `/excalidraw-assets/`; keep the build-time host rewrite over the engine's whole dependency tree and the CSP header without `unsafe-eval`; and keep the e2e network assertion.
- **Server egress exception: Miro import (reviewed, wave R).** The api, and no other process or the browser, may call `https://api.miro.com` (port 443; `/v1/oauth-token` and `/v2/` read paths only) and, for the file bytes a `redirect=false` resource answer points to, only the download hosts in `MIRO_DOWNLOAD_HOSTS` (`packages/contracts/src/miro-import.ts`). Each request goes through `apps/api/src/egress` (exact host allowlist, address vetted and pinned, redirects refused, deadline and byte caps), and only inside an import job a creator started with the access token they pasted for that job. The token is sent only in the `Authorization` header to `api.miro.com`, lives only in that job's memory, is never written to Postgres, disk, logs, audit rows, error messages or responses, and is dropped when the job ends. Miro content is untrusted: it reaches a board only through `packages/miro-import` and sync's per-element seed validation, and its files only through the normal upload limits and worker checks. No URL found inside Miro content is ever fetched. Tests use a fake Miro server behind the local-dev seam, never the real service. The one exception is `scripts/miro-probe.mjs`, which the owner runs by hand on his own machine with his own token (GET only, `api.miro.com` only, the token from the environment and never printed); no agent runs it.
- **Server egress exception: chat notifications (reviewed, wave R).** The api may POST notification messages to the incoming-webhook URLs that a workspace owner or admin who is a creator saved, and only to `https://hooks.slack.com/services/…` or a Teams Workflows URL on `*.environment.api.powerplatform.com` (`CHAT_HOOK_RULES` in `packages/contracts/src/chat-hooks.ts`), port 443, address vetted and pinned, redirects refused. A message carries only the event, display names, the board title, a link back to Lobby and, when that hook's admin turned it on, a comment snippet of at most 140 characters. It never carries element data, file names or contents, emails or signed URLs. A person's notifications are sent only after that person opted in for that hook, and every send re-checks their access to the board. A webhook URL is a secret: it is stored only encrypted (AES-256-GCM under `DRAFTROOM_WEBHOOK_SECRET`), never logged, and never returned to a browser beyond its hint. Tests use a fake webhook receiver, never Slack or Teams.
- The sync server uses only pure functions from `@excalidraw/element` (never `Scene`), installs the text-metrics provider at start-up, and builds server-made elements with `created: null` and kept ids.
- No production dependency may need a paid licence or carry a copyleft licence (CI licence check). The only tldraw code allowed is `@tldraw/tlschema`, `utils`, `store`, `state` and `validate` (MIT), inside `packages/tldraw-import`.
- Presence (cursors/selection) is ephemeral and never written to board storage.
- File processing (thumbnails, PDF pages, media probes) stays outside the live sync loop. Treat uploaded files as untrusted; impose size/page/pixel/duration/time limits.
- (Wave W) Machine-learning models are never downloaded by Lobby, at build or at run time: the owner places an approved file, the worker loads it from a configured path (`DRAFTROOM_BG_MODEL_PATH`) only when its sha256 matches the pin in `apps/worker/src/ops/bg-model.ts`, and every model is listed in `apps/worker/models/MODELS.json` with a permissive licence (`licence:check`). Inference (`onnxruntime-node`, CPU provider, its install script blocked by `allowBuilds`) runs only in a worker child process with a heap cap and a kill timer, never in the api, sync or browser. Tests use a synthetic model, never the real one.
- (From milestone 1) Every API, WebSocket, asset, worker, export and AI action enforces board/workspace permissions server-side; derive authorship from the authenticated session. Development identities exist only behind an explicit local-dev guard.
- Only creators create workspaces, projects and boards (in any form: new, template, sample, duplicate, import, restore as new) and hand out or raise access. A creator has a verified sign-in address on a creator domain (`DRAFTROOM_CREATOR_DOMAINS`, default `darkburn.com,trailerparkgroup.com,trailerpark.com`) or on the exceptions list (`DRAFTROOM_CREATOR_EMAILS`, set only in the Render Dashboard or API, never in git); Clerk test-mode addresses never count, and the rule fails closed. An email invitation works only for an account with that verified address; name-only guest links are unchanged. Contract: `docs/DOMAIN-ACCESS-CONTRACTS.md`.
- Do not show "Saved" until sync/persistence semantics actually support it. Do not claim a file is natively editable when it is a flattened preview.
- Keep secrets server-side. Never log session tokens, private content, signed URLs or OAuth tokens.

## Local environment (this Windows PC and the NAS)

- Node 24 LTS + pnpm 10 are installed but may be missing from the Git Bash PATH. Prefix: `export PATH="/c/Program Files/nodejs:/c/Users/Chase/AppData/Roaming/npm:$PATH"`.
- Board data lives in the configurable `DRAFTROOM_DATA_DIR` (default `./.data`). Never place SQLite databases on a network share (e.g. `V:\`).
- The NAS (`V:\` is its `/volume3/Apps` share; Docker over SSH) is approved for Draftroom's own containers only. Never stop, rebuild, edit or inspect anything of other projects there (`V:\theaitre-bot`, the `theaitre` compose project), and never read their `.env` or `secrets/`. Keep Draftroom on the NAS LAN-only unless the owner approves exposing it.
- Load tests may run on the NAS in throwaway containers named `draftroom-spike-*` (or `draftroom-load-*`), LAN-only with no published port, with SQLite on the NAS's own volume inside the container, never over SMB, and never with real board data. Build no image for them: run them from the Node base image that Draftroom's Dockerfiles pin (pulled once if missing; it stays), with a `git archive` of the source in their folder and dependencies installed by a throwaway install container, the only one with network access. Check free disk first and cap the folder, list everything by that name before removing it, remove the containers, the network and the folder after each run, and never touch other containers or images.
