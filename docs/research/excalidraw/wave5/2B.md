## What changed

### V3's medium: a key share the room admits no longer bricks a board (§5.9 step g)

3390b0c's key check failed the whole roll-forward with `INDEX_DUPLICATE` whenever an element the merge
wrote kept a key it shared with a tombstone. The room's index cache holds live elements only, so a raw
push can leave a live element on a tombstone's key; after a rollback, an R0 recolour or move of that
element left the board refused (4099 `CONVERSION_FAILED`, snapshot 503). Now (`rollforward.ts` f'):

- an element the merge writes that kept a shared key gets a key of its own next to it, on the side the
  room's `(idx, id)` order draws it (below the key when its id sorts before the untouched holder's, above
  it otherwise): the paint order is unchanged and no row the merge does not write is touched. It runs once
  every write is known (a re-fit, a re-snap or a symmetric `bound` can write an element too). The report
  lists it (`repaired: [{id, code: 'index-shared'}]`);
- a share between rows the merge does not write stays as the room stores it (`indexSharesKept`);
- only a key the merge assigned itself and that is not unique is refused (a merge fault: nothing written,
  the board stays closed with the report, as §5.9 g says).

Regression: `apps/sync/test/migrate/rollforward-keys.test.ts` (6 in-process cases: recolour, move, delete,
the two tie orders, an untouched share, a control) and `rollforward-keys-open.test.ts` (V3's real-process
repro: PREPARING, `rollforward:done`, snapshot 200, keys unique, the served paint order kept); both failed
on `f336ae4`. V3's own probes (`v3-probe-rf2`, `v3-probe-keyshare`, copied untracked) pass 7/7.

### Open item 10: R0's restores and trims mirrored into `lb_deleted`

During a rollback R0 removes rows from `dr_deleted_records` (a restore's `removeRestored`; `trimNow`'s
whole old batches). The roll-forward now drops, in its transaction, every converted `lb_deleted` row whose
source row is gone (same batch, the element ids derived from the record id), after appending R0's new
rows; rows of origin `live` are never touched, whatever their batch number; `dr_deleted_*` is only read
(`counts.deletedRowsRemoved`). The same test found that a record R0 brings back whose id `lb_elements` holds
only as a tombstone (restored after an earlier roll-forward deleted it) was skipped as `id-exists`: it is
revived now, theirs winning, and a deletion ours made since the last cycle is listed as `life`.
Regression: `rollforward-deleted.test.ts` (R0's own `restoreDeleted` and `DeletedStore.trimNow`, and a
second cycle), failing on `f336ae4`.

### Open item 12: how binding-record diffs map in local mode

Defined in `rollforward.ts`'s header and pinned by `rollforward-bindings.test.ts` (8 cases, each also
checking that every binding is symmetric afterwards): a binding record created, deleted or changed in
theirs touches both of its ends (a re-targeted one its old target too); the arrow's `bind` group (and its
`path` unit when the ends moved) merges per group, a both-sides change listed as `bind` with theirs
winning; a target's `boundElements` is derived from the merged arrows in step g, never merged from a
conversion, so ours' Excalidraw-era bindings stay listed, a binding to a deleted target is nulled (the end
stays) and a deleted arrow leaves its targets' lists; then the re-snap and the invariants. The cases pass
on `f336ae4`'s merge: a definition and its guard, not a fix. (The converter maps a precise tldraw binding to
`orbit` at its anchor and an exact one to `inside`; the plan's §5.1 row says `isPrecise` → `inside`.)

### D4: every tldraw geo kind is built, none dropped (§5.1, §5.2)

`packages/tldraw-import/src/geo-shapes.ts` is the converter mapping of tldraw 5.4.2's 20 geo kinds
(`GEO_SHAPES`):

| Build | Kinds | Lossy codes |
|---|---|---|
| native | rectangle, ellipse, diamond | none |
| native, approximated | oval (an ellipse; tldraw's is a stadium; the native type keeps Excalidraw's arrow binding) | `geo-approximated` |
| native with marks | check-box, x-box: the rectangle plus tldraw's check mark or cross as open lines in one group (the mark was dropped before) | `geo-polygon` |
| polygon, exact | triangle, pentagon, hexagon, octagon, star, rhombus, rhombus-2, trapezoid, the four arrows | `geo-polygon` |
| polygon, sampled curve | heart (tldraw's four Béziers), cloud (tldraw's seeded bumps, the shape id as the seed) | `geo-polygon`, `geo-approximated` |

The outlines are tldraw's own geometry (the 0.38 offsets, `getPolygonVertices` filling the box, `getStarPath`;
before, the converter had its own approximations), and polygons now close exactly. `CONVERTER_VERSION` is 2
(no board is converted in production yet). Regression: `packages/tldraw-import/test/geo-shapes.test.ts`
compares every kind with tldraw's `getGeoShapePath` (the web app's tldraw dependency, until wave 4): vertex
for vertex, the heart's Bézier samples, the cloud's bump ends and samples on tldraw's curve, the marks; and
converts all 20 kinds, labelled, flipped and rotated, into valid elements. The kitchen sink's pinned lossy
counts gain `geo-approximated` 1 (its cloud).

The roll-forward treats a geo built from parts as one shape for style (V3's part-3 low, open since): when
theirs restyled one part (tldraw's `color` lands on the outline) and ours another (an Excalidraw style write
may land on the holder), theirs wins for the whole shape and the part ours styled is listed. V3's property
probe now lists seeds 207 and 225 (seed 105 fails on the probe's own expectation, as V3 said).

### V3's lows: the leak check and the evidence wording

`e2e/spike-b/b8/leak-check.ts` looks at every file in its scope: text by content (no NUL in the first
64 KB), so `.jsonl`, extensionless stdout captures and `.excalidraw` exports are searched; files over 64 MB
in overlapping chunks; binary files (SQLite copies) as UTF-8 too, gating outside `SPIKE_B8_DIR` and counted
apart inside it (the data dirs §8.6.7 allows); compressed files counted by extension; an unreadable file
fails. `leak-match.ts` also removes ANSI codes and zero-width characters, applies NFKC, folds case, decodes
percent-encoding (URL and form) and base64 runs, and finds a copy cut short by the first and last 16
characters of every string of 24 or more. Twelve new cases on a synthetic canary (V3's `canary2` variants:
url, form, upper, zero-width, ANSI, truncated, base64, jsonl, no extension, `.excalidraw`, a 3 MB file read
in chunks, a SQLite copy outside and inside `SPIKE_B8_DIR`) fail on `f336ae4`.

Wording (`B8.md`, `M3-fixes.md`): "unit 407/407" counted 280 of V3's untracked probe tests (O4's own count
is 127/127); one generated run spanned the `38af6d6` merge; "V3 confirms" came before the confirmation.

### R0's contracts 3 and 4 on the Excalidraw build: backups

One engine per process (`apps/sync/src/backup/engine.ts`, set by `app.ts` and the restore tools from
`DRAFTROOM_ENGINE`); the tldraw build keeps R0's rules unchanged (the R0 and backup suites pass as they
were).

- **Description.** A converted board is described from its `lb_*` tables as `lobby-elements-converted`
  (the `lb_*` digest, `lb_meta.clock`, the element rows), a format R0 keeps listed, signed and under
  retention and refuses to drill or restore by name; a board born on the new canvas stays `lobby-elements`.
  Both list the files their elements reference (`customData.lobby.file`).
- **Local backups.** `backup/element-backups.ts`: every backup interval, each board whose `lb_*` state
  moved since its newest backup is copied through a read-only connection in one backup step (one read
  transaction; no room opened, the board file never written); tldraw-only boards are left to their
  pre-cut-over backups. It is run-all's per-board backup on this build too (`app.ts`). Backups of one board
  run one at a time process-wide (a run-all meeting a pass on one board lost a manifest entry otherwise).
- **Retention.** Local (`backup.ts`) and offsite (`offsite-manifest.ts`) retention keep every backup whose
  `holdUntil` is ahead outside their count (the same code as the tldraw build); the entry is signed with its
  format and `holdUntil`, so changing either invalidates it, and an entry that fails its signature is never
  trusted for retention.
- **Drill.** `lobby-elements` and converted backups are restored into a clean dir and opened through the
  element room's store (`room/store.ts`, loaded lazily so the tldraw build never loads it): the clock and the
  element count must be the entry's and every row readable; from the local folder and the offsite store.
- **Staged restore.** An lb backup goes back with a new epoch and a clock past the live one (every open tab
  resets); a tldraw backup from before the cut-over goes back as it is and is converted when its room opens
  (§5.6). R0's lb carry is R0's rollback rule only.

Regression: `apps/sync/test/backup/excalidraw-backups.test.ts` (7) and `excalidraw-backups-process.test.ts`
(a real Excalidraw sync: its periodic pass and run-all), failing on `f336ae4` (the process test also fails
with `app.ts` alone reverted).
