## What the spec does

Three Chromium processes and 50 headless clients (O2's engine core, loaded through `e2e/load/headless.ts`)
run random ops for 10 minutes. Each headless client is a dev user with a grant, and every connect uses a
fresh 60 s api ticket.

**Browser ops**, through the facade or the keyboard:
- create a note;
- move, recolour, group (own elements);
- delete;
- text through the lease (select, Enter, type, Escape);
- Ctrl+Z;
- bind: an arrow between two own notes, as engine fields with `startBinding`/`endBinding`.

**Headless ops**, on the client's scene with Excalidraw's version bump:
- create (`buildStickyNote`);
- move, recolour, group;
- delete;
- label text.

The headless client has no undo stack, so undo is a browser op only.

**Disruptions:**
- Every 45–90 s, either a browser's socket is cut for 3–8 s (the relay), or a headless client is
  dropped and replaced after 3–8 s.
- Once, at a random minute in [3, 7], sync gets a SIGKILL and is restarted 3 s later.

**Pass conditions:**
- After a final quiesce (every tab shows Saved and every client is saved), all 53 maps hash equal to the
  test snapshot, tombstones included (`closeWindow`, with its horizon check).
- 0 invariant violations.
- 0 acked-but-missing. Each client changes only elements it created, and keeps a ledger of their
  tracked fields (`x`, `y`, `backgroundColor`, `isDeleted`, `groupIds`) as last acked:
  - headless clients record from their acks;
  - browsers record every 2 s while the tab shows Saved, which means everything so far is acked.
- The acked-but-missing comparison runs right after the restart, once every client is back. An element
  is compared when its ledger entry predates the kill and its writer did not push it again before the
  kill. Such an element must be stored exactly as the ledger says. The number of elements checked is
  in the evidence.

## Deviations from the check as written

- **Undo:** browsers only (the headless client has no stack).
- **Bind:** only between a client's own notes, so an arrow's targets have a single writer.
- **Acked-but-missing:** covers the elements whose state was settled at a Saved moment before the kill.
  An element pushed in the last moments before the kill is left out of the count and not compared.
- **The kill replaces every headless client.** After the SIGKILL and restart the spec drops and
  reconnects all 50 headless clients (fresh cores, fresh tabs), so a create a client made while sync was
  down, never acked, is lost with its old core. That is why a run stores about 40–60 fewer
  headless-created elements than the clients made (never acked, so not acked-but-missing).

Why it was rare: it needs this tab's create in flight and re-keyed locally by a tie, a third client's
create landing on exactly that local key in the same batch that confirms this tab's create, before its
ack, and an id order that puts the other element second. The restart makes the first two likely: every
client replays the creates it made while sync was down, all on the same top key, in one burst, and
fractional keys are deterministic (`generateKeyBetween('bVj', null)` is `bVk`, both for A's local re-key
and for the server's fix of C's note).

### Reproduced; what `319d532` had already changed

`apps/web/src/canvas/sync/core/inflight-key-echo.test.ts` plays that frame order against the engine core,
on a scene that does to index keys what `updateScene` does (`syncInvalidIndices`: in place, version + 1):

- **On `017f76d`'s engine** (a temporary checkout, removed after): Saved with 0 pending, the other user's
  element at `a3`, version 2, in the map, against the server's `a2`, version 1, and nothing pushed for it.
  That is B11 run 1's divergence, deterministically.
- **On `99ac6c5`** (before the fix): `echo_suspect`, then the core pushes the other user's element's new
  key (`{"k":"p","id":"z1","pv":1,"g":{"z":{"index":"a3"}}}`). The maps converge, which is why B11 passes,
  but A has written an element it never edited (an echo, B10's class). The change came with `319d532`
  (spike B O2 part 3, 2026-09-29 18:39 -0700, after the third pass above): every server message, flush,
  persist and adoption first scans the live scene (`syncLive`), so the in-place bump is classified and
  pushed.
- **With the fix** (`bf45f19`): neither. Both test cases (the run-1 order, and a reorder not pushed yet

At `99ac6c5` the echo is frequent in B11: in the 10 passing runs that counted it (below), every run had

### The fix

`LobbyEngineCore.applyScene` (`apps/web/src/canvas/sync/core/engine.ts`): the index pre-pass also counts as
this client's to re-key a confirmed element whose scene key differs from the server's and is this tab's own
unconfirmed write (`z` in flight or dirty): a create whose `changes` came before its ack, or a reorder in
flight or not pushed yet. It is re-keyed between its confirmed neighbours (in flight: locally; unsent: the
new key is what goes out), so no confirmed element can tie with it. A confirmed element whose scene key is
the server's is treated as before. Checks at `bf45f19` (this PC, while no B11 run was going): the new
test 2/2; the web project 223 files, 2,251 tests; the sync suites that drive the core against the room
(headless, verifier-v1, convergence, conflicts, element harness, ticket transport) 15 files, 45 tests;
engine-probe and the arrows acceptance 17 files, 115 tests; spike B's B10 (echo: 50 + 50 creates at the
top, the watcher pushes nothing) 1/1 on base 7850; all passed. Not run: the whole `sync` project, the
default e2e suite and the rest of spike B.

### Open (not SYNC-4): a headless join can wait 30–120 s late in a run

The connect records show what stopped runs 4 and 11, and run 25 here. Of the 17 chaos-loop reconnects in
the 6 runs above, one per run was slow: its socket got **no frame for 30 s** before the first welcome, so
the heartbeat closed it (4000), and a retry more than 65 s after the ticket was issued was refused (4099).
Those 6 clients (7 attempts) waited 29 to 123 s; they had dropped 353 to 567 s into the window, with 53
sessions writing. In the 5 passing runs the slow join completed only
at 601–605 s, as the run's 10-minute loops stopped; in run 25 the re-ticketed attempt stalled too (123 s,
refused), the chaos loop never reached its SIGKILL, and the run has no verdict. The other 11 chaos-loop
reconnects (some as late as 513 s) and every SIGKILL's 50 reconnects joined in under 10 s. This test
process (which runs the 50 headless cores) was late by a mean of 60–82 ms and at most 1.2–1.7 s on its
20 ms timer, so it did not stall for 30 s; the silence came from the other end. Two facts of the room's
code fit it but are not shown to be the cause: a reset welcome waits for the gzip snapshot (a promise in the
session's FIFO queue, `room/outbound.ts`), and the pong to the client's ping queues behind it. Not
determined, and not fixed here. Next: keep the sync's output per stack (today only in the launcher's
memory), log hello-to-welcome time per session in the room, and repeat with a new tab id per reconnect to
rule the reused session id in or out. Browsers re-ticket each reconnect, so a person would see a long
"Connecting" rather than a refusal.
