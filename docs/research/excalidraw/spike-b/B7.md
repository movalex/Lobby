## The M1/M2 export failure: the probe read the SVG's centre, not the image's

The lead's M1/M2 run failed only the last pixel of "exports". Not an export bug: Excalidraw's SVG
renderer (`chunk-FN755BR4.js` 4253-4330, dev build) writes each file **once** into `<defs>` as
`<symbol id="image-<fileId>"><image href="<dataURL>" width="100%" height="100%"></symbol>` and draws it
with `<use href="#image-<fileId>" width height>` inside a translated `<g>`. The spec located
`svg image`, the `<image>` inside the symbol, which is never rendered itself; Chromium reports its box as
100% of the SVG's viewport at the SVG's origin (a standalone probe: the `<image>`'s box
`{x:0, y:0, w:400, h:300}` for an SVG of 400 × 300, the `<use>`'s `{x:96, y:16, w:64, h:48}`). So the
probe sampled the centre of the whole export, which lay between the image and the "Font check" text:
white. The spec now reads the pixel at the centre of the drawn `<use>` (64 × 48 px at (64, 16) in every
run, red `[220, 41, 40]`), and also checks what the lead asked: the SVG embeds the image **bytes**:
every `<image>` href is `data:image/<type>;base64,…` (here `image/webp`, the 84-byte thumb derivative),
and the symbol's payload equals, byte for byte, the derivative the loader fetched from same-origin
`/files/<ast>/<ver>/d/<drv>?board=`. `exportFilesMap` (export/svg.ts) already built that export-only
map from the runtime `blob:` URLs; no app code changed.

## Lost creates (O2): a `transact` create can vanish before it is pushed

Found by the first valid mood-board run (the M1/M2 lead run of "mood board" alone was not valid). In
run 1, 1 of the 200 images placed with `placeFile` (one `CanvasPort.transact` create each) was never
stored: the snapshot held 199 of them, and B's loader loaded every stored image (201: the 199, the first
image and the PDF face). Two scratch probes before the runs showed the same
(3 and 1 of 200 lost; each lost element was in neither tab's scene, in no push of either tab, and both
tabs showed Saved with `lastReject: null`).

`b7-probe-lost-create.spec.ts` isolates it: one tab, no other writer, 400 rectangles through the
facade's `create` (= `transact`) with 0-25 ms gaps. **Every run lost creates** (runs 1-3: 3, 2 and 3 of
400); every lost create had an inbound board-socket frame before the next
create (in a tab with no other writer, typically the ack of an earlier push; about a quarter of all
creates had one, and 2-3 of those were lost: by the mechanism below, the frame must be handled before
Excalidraw reports the create); none was
pushed or stored; the tab said Saved with no reject.

The mechanism, from reading O2's code (not changed by O5): `port-impl.ts` `transact` installs its array
with `api.updateScene` (captureUpdate NEVER), and the core learns of it only from Excalidraw's next
`onChange`, which Excalidraw fires in `componentDidUpdate` (dist/dev/index.js 49432-49548), i.e. after a
React commit that React schedules for an update made outside a React event. When a socket frame is
handled in that window, `onAck` / `onChanges` call `applyScene(affected)` (`sync/core/engine.ts`), which
builds the new array from `this.currentOrder`, the scene as of the core's **last scan**, plus confirmed
elements, and installs it with `scene.apply`: the new element is neither there nor confirmed, so it is
dropped from the scene before any scan saw it, and `readScene(next)` forgets it too. Nothing then pushes
it, and Saved stays true (AGENTS.md: "Do not show Saved until … persistence semantics actually support
it"). Any `transact` outside a React event is exposed: the facade, O5's file placement, tags, +1, the
mind-map collapse, and any future feature or paste path.

Suggested fix (O2's decision): before any server-driven `applyScene`, scan the live scene first
(`const live = this.scene.read(); if (live.elements !== this.currentOrder) this.scan(live)`), so local
changes Excalidraw has not reported yet are tracked (a new element becomes `isNew`) before the rebuild;
or have `transact` hand the core the scene synchronously (`core.onSceneChange(scene.read())`) after its
`updateScene`. The probe's pass condition (0 of 400 vanished, 0 never pushed, 0 not stored, Saved) is
the acceptance test; B7's mood board should then pass 3/3 as runs 2 and 3 did.

## Decisions and deviations

- **A1 `foreign`** is every existing version the board cannot serve by the `/files/…` routes' own rule
  (`files/serve.ts` `loadBoardVersion`: uploaded to that board, or linked to it inside its workspace
  through `board_asset_links`). So a version of another board **in the same workspace** without a link is
  `foreign` too, not only another workspace's. Stricter than "another workspace", and consistent with
  what the loader could fetch; B6 F9 (another workspace → `INVALID`) is unaffected.
- **SVG images.** Today's api never makes an SVG an `image` (`INLINE_MIMES.image` has no SVG, so an SVG
  upload is kind `other`). The rule is still built: the resolver asks for an SVG's original only when it
  has no raster derivative, and the loader hands any SVG response to the engine as a runtime-only
  `data:` URL, never `blob:` (unit-tested). The B7 browser run cannot produce one.
- **Derivatives by zoom** (`files/derivatives.ts`, 512 device px for 300 ms → `@display`, ≤ 60 per
  session) are built and unit-tested but **off** on the board page: switching a scene element's local
  `fileId` to `ver_X@display` needs O2's adapter to strip the suffix on the wire (E9). Until then an
  upgrade would push an invalid `fileId`. B7 reports "derivative upgrades: 0 (opt-in)".
- **Placeholder.** Lobby's own placeholder is an overlay (`[data-lobby-image-placeholder]`) over the
  engine's pending grey (`#E7E7E7`), shown while the loader has not handed the image over or gave up.
- **The loader instance** is created by O5's features when the board page attaches its engine
  (`installBoardOverrides` → `onBoardEngine`), one per page. O2's board page must not create another.
- **Images without `customData.lobby.file`** (for example a converted board if the converter does not
  write it) cannot be resolved: the meta route needs the asset id. They show the placeholder. Wave 2 needs
  either the converter to write `file` on every image or a browser route that maps a version to its asset.
- **The file-card viewer** is a minimal one (the worker's page renderings); `file-card/PdfViewer.tsx` is
  tldraw-bound and moves in wave 3.
