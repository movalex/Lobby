## What the spec does

- Browsers: A, B and C are three separate Chromium processes (`chromium.launch()` each; the evidence
  records their PIDs). Each is signed in as its own dev user through the real dev login. A owns the
  board, and B and C are editors.
- The actions are released together, in one of two ways:
  - The facade writes are armed inside each page for one wall-clock instant (`runTogether`). Every
    process on the machine reads the same clock.
  - B1.1's pointer-up of B's real drag and A's write are released by one Node barrier
    (`releaseTogether`).
  - Each repetition records its release spread. A repetition over 20 ms is repeated (at most 3 tries)
    and never counted.
- After every repetition:
  - every tab shows Saved;
  - `closeWindow` checks that the three maps (tombstones included) hash equal to the test snapshot and
    that the invariant checker finds nothing on the snapshot;
  - a repetition whose `horizon` moved is invalid and re-run (§8.1).

| Case | Action | Pass as coded |
|---|---|---|
| B1.1 | A sets `backgroundColor` through the facade. B drags N with the real pointer (down, 10 moves) and lets go on the barrier. | The snapshot's N has A's colour and B's dropped `x`. C (receiving only) pushes 0 ops (B10 log) |
| B1.2 | A adds `tag:x`, B adds `plusOne:<B's uid>`, C moves N by (60, 30), all armed together | The snapshot has all three |
| B1.3 | A sets the label's `fontSize`/`baseFontSize` to 28. B sets N's fill. C groups N, its label, M and its label | All three kept |
| B1.4 | A deletes N while B moves it. Even repetitions put A's delete first, odd ones B's move (40 ms apart) | N is a tombstone in the snapshot and in all three browsers. C pushes 0 ops |

Setup: `tagDef:x` goes onto the board's doc once, as a raw push from A's page (`forgeSession`). This is
setup, not the action under test, because the facade has no doc verb (§6.3).

## Assumptions to confirm at integration (O2's port)

- `create('note', { x, y, text })` makes a note with its label (the text is needed for B1.3).
- `update(id, { customData: { key: value } })` sets `customData.lobby` keys, as the port comment says.
- `fit([ids])` on the facade side channel frames N for B's drag.

## Harness readiness (runnable before M1)

These are the harness's own checks, in `e2e/spike-b/support/selftest/`. They ran on O3's branch
before M1.

- **units:** the barrier, the push recorder, the stack guards (backups off, no R2 variables, a base the
  web build serves), dev handles, lease-hook bodies, and the convergence and divergence logic.
- **stack:** sync runs on the TLDRAW engine, because O1's room is a stub until M1. This part checks:
  - the launcher (e2e/tests/support/stack.ts, reused);
  - dev sign-in and the board grants;
  - two browser processes with different PIDs;
  - a forge socket opened with the page's own ticket;
  - the relay's added latency, the cut (the live socket closed with code 1012, the reconnect held
    with its frames recorded), and both restore modes;
  - the test routes answering 404 until a room registers its hooks.
- **barrier:** three Chromium processes on spike A's `/spike/engine` page, 20 in-page releases and 20
  Node-barrier releases.

Command: `bash docs/research/excalidraw/spike-b/scripts/o3-checks.sh selftest 3`. Base 7880, a fresh
web build each run. 7880–7899 was free before and after.

The machine was shared: other agents ran e2e on 6600–7049 at the same time. So none of these numbers
comes from a quiet window.

**Deviation, found and fixed.** In the pass before this one, run 1 failed one unit assertion of O3's own
test. It expected parties that `setTimeout` spaced 60 ms apart to arrive at least 50 ms apart, and the
spacing measured 48 ms (Windows timer granularity). The assertion is now ≥ 40 ms. The barrier code did
not change. In that pass, a later run measured the Node barrier's completion spread at up to 14 ms
(CDP under the shared load). The start spread stayed ≤ 1 ms. The release spreads above are
`Date.now()` in each page (ms resolution), so 0 means within the same millisecond.
