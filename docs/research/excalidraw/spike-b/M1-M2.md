**O2 (web engine)**
- **L10 5, "B's move first", intermittent: B's move of a centred free text was lost 20/20 in the first run
  (`2a1944e`, a loaded machine) and kept 20/20 on the rerun (`9b6fb7e`).** In the failing rows the stored
  text is back at A's old `y` (73,000; B's 73,050) and centre, and the row trace shows A's copy still at the
  old position after C had B's move. A lead reading of `sync/core/engine.ts` (not confirmed with a trace;
  the run's trace was overwritten): while A's fit is in flight, `rebuild` keeps the fit's local `x`, `y` over
  the server's copy, so A's scene does not take B's move; `staleFit` drops only an unsent fit. A's next
  keystroke can then diff the old position against B's confirmed one and send `x`, `y` as a new fit on a
  base that includes B's move, which the server accepts. The window depends on timing (the relay latency
  against A's typing), which would explain 0/20 then 20/20. O2 should reproduce it with a longer latency
  and close it (a remote `pos` write on an element with an in-flight fit should also drop that fit's hold).

  run's trace was overwritten (the lead's runner now keeps every spec's output).

  must keep `customData`.
