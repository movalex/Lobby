## What the tests show

Reproduction of probe1 (engine behaviour, pinned):
- `syncInvalidIndices([A a1, B a1, C a2])` mutates **B** in place: `a1 → a1V`, version +1; A untouched
  (element `index.js:12728-12736`, `getInvalidIndicesGroups` 12766-12821, `isValidFractionalIndex` 12822-12841, `generateIndices` 12842-12860).
- `new Scene().replaceAllElements(…)` — what `App.updateScene` calls (excalidraw `dist/dev/index.js:43825-43846`
  → element `index.js:19079-19085`) — does the same.
- **The echo case**: my new `X0` created at the top got `a1`; the server meanwhile gave `a1` to Bob's `c2`. In
  Excalidraw's (index, id) order `X0` sorts first (`'X' < 'c'`), so `updateScene` re-keys Bob's confirmed `c2`
  and bumps its version: exactly the echo of §2.5.5 E2. Reproduced in Node and in the browser.

With the pre-pass (all through `Scene.replaceAllElements`, and Excalidraw's own `validateFractionalIndices`
with `shouldThrow: true, includeBoundTextValidation: true` on the output):
- my colliding element is re-keyed strictly between its confirmed neighbours (`a1V`), the confirmed ones keep
  key and version, and `updateScene` then changes nothing at all;
- a collision with a **tombstone** (deleted confirmed element) is resolved on my side (deleted elements are in
  the array `updateScene` gets, so they would be re-keyed too — open item "index collisions with deleted
  elements");
- null and invalid keys on my elements are assigned at the top;
- **E3**: my new label keyed below its confirmed container is moved just above it (`label-order`);
- the in-flight flag is reported per re-key (a re-key of an element already sent stays local; the server's
  `fix` wins);
- 50 concurrent creates at the top by each of two users: the receiver re-keys only its own 50, keeps their
  relative order, 101 unique keys;
- confirmed elements that collide with each other (a broken server invariant) are reported
  (`confirmedConflicts`) and never touched;
- property test: 600 random scenes (1–25 confirmed incl. 15% tombstones, 1–8 of mine with colliding, null,
  invalid or top keys, sometimes a label under a confirmed container, shuffled input): the assertion never
  fired, every key valid and unique, every confirmed key unchanged.

## Engine behaviour recorded (differs from the plan)

1. **E3 "dev builds throw otherwise" is not true for the npm packages.** The bound-text order check lives in
   `validateIndicesThrottled` (element `index.js:18947-18958`), which runs only when `isDevEnv() || isTestEnv()`
   (from `@excalidraw/common`) or `window.DEBUG_FRACTIONAL_INDICES`. Common's `import.meta.env` is
   `{ DEV: true }` in `dist/dev` (common `index.js:34`) and `{PROD:!0}` in `dist/prod`, with no `MODE`, so
   `isDevEnv()` (common `index.js:2945`) is always false. And `syncInvalidIndices` never fixes label order
   (element `index.js:12713`: "we don't autofix invalid bound text indices"). Result: a label sorted below its
   container is **accepted silently and not fixed**; with `window.DEBUG_FRACTIONAL_INDICES` it only logs.
   Lobby's pre-pass (client) and the server's step 11 are the **only** enforcement of E3. Pinned by
   `apps/web/test/engine-probe/node-probes.test.ts`.
2. The check is also throttled to its first call per 60 s (lodash throttle, leading edge).
3. **In plain Node, `Scene.replaceAllElements` throws `ReferenceError: window is not defined`** on its first
   call in any 60 s window (`window?.DEBUG_FRACTIONAL_INDICES` — optional chaining does not guard an undeclared
   global, element `index.js:18949`), and the throttle's timer keeps the process alive for 60 s. The sync
   server must never use `Scene`; the Node test stubs `globalThis.window = {}` to emulate a browser, where
   `window` exists and the flag is unset.

## Deviations from the plan

- The plan's pass criterion is "dev assertion silent". The assertion is implemented as
  `assertConfirmedUntouched(before, after)` (throws `EchoSuspectError`, code `echo_suspect`; production passes
  `onViolation` for a metric). It compares `version` and `versionNonce` of confirmed elements between the array
  handed to `updateScene` and the scene afterwards. It was also shown to **fire** in the unprotected case, so
  "silent" is meaningful.
- Cost: the pre-pass sorts the whole array; 14.7–15.2 ms at 20,020 elements (Node, this PC). The adapter
  should skip it when there are no own unacknowledged elements, or run it on the changed neighbourhood only,
  if B's perf runs show it on the apply path.
