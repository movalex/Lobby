## Engine behaviour (file:line in the installed 0.18.0-1118751 dist)

- **E1 confirmed.** `App.updateImageCache` (`@excalidraw/excalidraw/dist/dev/index.js:47091-47111`) calls
  the element package's `updateImageCache` (`@excalidraw/element/dist/dev/index.js:22619-22660`: an
  `HTMLImageElement` `onerror` puts the id in `erroredFiles`, :22646) and then replaces every image
  element of that file with `newElementWith12(element, { status: "error" })` (:47101-47104) under
  `CaptureUpdateAction.NEVER`. It is a new element version (v2 → v3 here), so `onChange` reports it and
  an adapter would push it. The plan cited 47089-47111; the function starts at 47091.
- **A failed image is never retried in that session**, which is stronger than "not retried by the
  engine": the errored entry stays in the image cache (the cache is set before the load is awaited,
  element :22637-22641) and `addNewImagesToImageCache` only loads ids the cache does not have
  (`index.js:47113-47118`); `addFiles` → `addMissingFiles` skips an id that is already in the files map
  (`index.js:43789-43821`, "if file already exists in editor state, the file data is not updated").
  Measured: after the URL works and the same file is added again, 0 new requests and `status` stays
  `error`. Lobby must therefore never hand Excalidraw a file that has not loaded; a retry is only
  possible outside the engine.
- **An image whose file is absent is harmless.** `updateImageCache` only looks at ids present in the files
  map (element :22628-22630), so an element whose bytes Lobby has not added yet is drawn with the pending
  placeholder (`drawImagePlaceholder`, element :13559-13572, `#E7E7E7` light / `#2E2E2E` dark, the icon
  from a `data:` SVG at :13551) and never marked. That is why the loader only calls `addFiles` after the
  blob decoded (`img.decode()`).
- **SVG must never go in as a blob: URL.** `addMissingFiles` re-encodes an `image/svg+xml` file by
  parsing its `dataURL` as a data URL (`index.js:43806-43818`); a blob: URL throws there (caught and logged).
  The loader only accepts raster types (`rasterMimeType`); Lobby's derivatives are WebP or PNG.
- New image elements default to `status: "pending"` (`newImageElement`, element :16656); Lobby's server
  stores `'saved'` (plan §2.10.1).
- A successful `addFiles` of a decoded blob changes no element version (0 ops in tests 2 and 3).
- **Every `addFiles` call repaints the whole scene** (`App.addFiles` → `clearImageShapeCache`,
  `scene.triggerUpdate()`, `addNewImagesToImageCache`, `index.js:43789-43796`). On the heavy board (A14)
  handing 200 images over one by one kept the board busy for 4.9-6.5 s after it opened (one full static
  render per image at fit). The loader therefore batches decoded files into one `addFiles` per animation
  frame; the A14 numbers of the final code are with batching.

## Deviations from the plan, and why

- The "engine" that "pushes nothing" is a probe, not the real sync adapter (spike B builds it). It counts
  exactly what the adapter would diff: element version changes relative to the applied server copy,
  via `api.onChange`, plus a direct version scan that does not depend on `onChange`.
- The loader's retry window is 5 minutes and the delays are 1, 2, 4, 8 … s, capped at 60 s: the plan says
  "retries at 1, 2, 4… s up to 5 minutes"; the cap is my choice.
- The loader's `resolveUrl(versionId, derivative)` returns a same-origin path; it refuses absolute and
  protocol-relative URLs. Lobby's real route needs the asset id, the derivative id **and `?board=<id>`**
  (`apps/api/src/files/serve.ts:58-63`, 400 `INVALID_BOARD_ID` without it; found in the A12 CSP run),
  so wave 3 feeds it from `meta-store` (asset metadata), not from the element.
- Blob URLs are revoked only on `dispose()`: the engine may re-create an `HTMLImageElement` from the
  files map (for example `exportToCanvas` loads every file again, A11), so revoking after the first
  decode would break later exports.
- B7's 200-image mood board is measured in A14 (the heavy board carries 200 images through this loader:
  at most 6 fetches in flight there too).
