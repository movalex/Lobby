## The case (x 20 per run)

1. A sticky note `n17` (200 x 200 at 200,150, label `Hello`) and an arrow whose END is bound to the
   note's bottom centre (`FixedPointBinding { fixedPoint: [0.5, 1], mode: 'orbit' }` plus the note's
   `boundElements` entry; see the converter finding below for why it is bound by hand).
2. Click the note, Enter: the lease is granted (30 ms) and the editor opens with the caret at the end;
   type ` World from the holder` (the label now wraps at 200 px); put the caret at offset 3; tag the
   textarea DOM node.
3. **Remote move** (+120, +40) through `applyRemote`. Then: same textarea node, focused, value and
   caret (3,3) unchanged, the textarea moved by exactly (120, 40) px at zoom 1 (tolerance 1.5 px), the
   label moved by (120, 40) scene units.
4. **Remote resize** (width 300, height 260, baseHeight 260). Then: same node, focused, value and caret
   kept, the textarea re-centred right and down.
5. **Holder re-fit** (`refit()`): the label re-wraps for 300 px (the `\n` goes away).
6. **Typing that outgrows the note**: Ctrl+End, one paste-sized insert (4 x 140 characters) and ` the
   end` typed key by key; the note's height grows past 260 (observed 392).
7. **Remote shrink** back to 200 x 200 (another user's resize, carrying that user's own `height` 200).
   Then: the note is still exactly 200 x 200 (updateScene re-lays nothing out, E7), the same textarea
   node is focused and its value is unchanged. **Holder re-fit**: the note grows again (width and
   `baseHeight` stay 200, `height` > 200), and that container write is classified `fit` with no
   `pos`/`shape` group (plan §2.9.4 rule 4, the B3 L6 situation).
8. **Ctrl+Z, then Ctrl+Y, inside the textarea**: the value goes back to a prefix and forward again
   (native textarea undo); Lobby's key actions and the registered `undo`/`redo` actions are called 0
   times.
9. Escape: the stored `originalText` equals the final textarea value; the lease is released.
10. Pass per case: all of the above, the arrow binding in place, and **every container write in the
   holder's window classified as `fit` with no `pos`/`shape` group** (at least one: the growth).

## What Excalidraw writes while the holder types (open item 3)

Aggregated over the recorder's steps of the last case of each run (the same in all three runs). "Local" = what the engine
wrote on this client; remote values are excluded.

| When | Element | Fields written (besides `version`, `versionNonce`, `updated`) | Group (§3.2) | Where in the dist |
|---|---|---|---|---|
| after the remote MOVE is applied | label | `x`, `y` | `layout` | `updateWysiwygStyle` on `scene.onUpdate` (25600-25607) ends with `app.scene.mutateElement(updatedTextElement, { x: coordX, y: coordY })` (25212) |
| holder re-fit after the remote RESIZE | label | `text`, `width`, `height`, `x`, `y` | `layout` | `handleTextWysiwyg` -> `updateElement` -> `getStickyNoteLayout` (49806-49838) |

| holder re-fit after the remote SHRINK | container | `height` only (grows back past 200; `width`, `baseHeight` stay 200) | **`fit`** | `getStickyNoteLayout` -> `height = max(baseHeight, text height + inset)` (element 6964-7040) |
| same | label, bound arrow | as the re-fit rows above | `layout`, `shape` | as above |
| typing | container (sticky note) | `height` only | **`fit`** | `newElementWith(_element, stickyLayout.container)` (49822-49824): `x`, `y`, `width`, `baseHeight` are written back unchanged for an unrotated note, so only `height` changes |
| typing | label | `originalText`, `text`, `fontSize`, `width`, `height`, `x`, `y` | `text`, `layout` | `updateElement` (49806-49838); `fontSize` shrinks before the note grows (fitStickyNoteFont, element 6906-6963) |
| typing | bound arrow | `points`, `width`, `height` | `shape` | `updateBoundElements` (49845) and, for the text element itself, the `onChange` wrapper (49864-49868) |

- **Open item 3 is confirmed.** Every keystroke that changes the note's geometry also rewrites the bound
  arrow's `points`, `width` and `height` from the holder's LOCAL copy (element `updateBoundElements`,
  element dist/dev/index.js 9055-9123 -> `LinearElementEditor.movePoints`). The arrow's `x`/`y` stay
  because its free start point does not move. These are ordinary `shape` writes on another element, so
  without a rule they would overwrite a concurrent edit of the arrow. It is worse after remote changes: the
  remote updates moved and resized the note but (as the server would send them) not the arrow; the holder's first
  re-fit then rewrote the arrow's geometry from its own copy (the `bound-arrow@refit` row). For other
  containers the same happens in `textWysiwyg` itself (`updateBoundElements(container, app.scene)` after
  the container height changes, 25133 and 25147).
- **Proposed rule (for B3 L6 and L10):** classify the bound-arrow endpoint writes made in the holder's
  editor window as **fit-derived**: sent in the same op batch as the container's `fit`, with the same
  `base`, and dropped with it when the server drops the fit (`fitDropped`). Or: the server recomputes
  the endpoints of arrows bound to a container whenever it applies a `fit` and clients never push them.
  The second is simpler for the client and keeps one writer; it needs the element package's binding
  helpers on the server (they run in Node, A3).
- The remote move itself is NOT written back to the container by the editor: the recorder shows no
  container write after `applyRemote` (only the label's `x`/`y`). §2.5.4's assumption "Excalidraw's
  editor follows scene updates" holds (`scene.onUpdate`, 25600-25607).
- The label's re-position after a remote move (`x`/`y`) is the holder's `layout` write: correct under
  the lease (only the holder writes the layout), but it is a local change caused by applying remote
  state; the engine must not treat it as an echo violation while a lease is held.

## Other engine behaviour

- `updateScene(..., NEVER)` with the editor open does not recreate or blur the textarea: the tagged DOM
  node survives both remote updates, and its value and selection are untouched (Excalidraw sets
  `editable.value` only at creation, 25247, and `onUpdate` only restyles and re-focuses).
- Ctrl+Z / Ctrl+Y in the textarea: Excalidraw's container `onKeyDown` returns early for a writable
  target (44005-44011), so neither Lobby's key action nor the registered `undo` action runs; the browser's
  native textarea undo reverts the typing. The replayed keys of A2 go through `execCommand`, so they are
  on the same native stack.
- **Converter finding (for [DATA] and A3):** `convertToExcalidrawElements` cannot bind an arrow skeleton
  to a sticky note: `bindLinearElementToElement` only builds `rectangle`, `ellipse`, `diamond` and `text`
  targets; a `stickynote` target hits `assertNever` and then `bindBindingElement(…, undefined)` throws
  `Cannot read properties of undefined (reading 'id')` (element dist/dev/index.js 24382-24441). The
  converter and server-made notes must build note bindings themselves.

## Deviations from the plan

- Spike A has no sync engine; "the holder re-fits with `fit`, not `pos`/`shape`" is shown by the
  classifier on the holder's local writes, which is the decision the adapter will make.
- The growth step uses one large `insertText` plus typed keys (typing 560 characters key by key would add
  a minute per case); both go through the same `input` -> `updateElement` path.
