# A16: every editor-open path goes through the lease

**Status: FAIL as written** (the plan's wording, 3 points, unchanged; see Verdict). **The security
property did NOT hold in the first version of this check** (see "Correction"). After the fix (`f17ce48`)
it holds: the old spec and the new regression spec pass 3 of 3 runs, 20/20 per case. Windows 11,
Node 24, Playwright 1.63.0 headless Chromium shell (touch cases with `hasTouch: true`), engine
0.18.0-1118751.

Plan §8.2 A16 (with revision 3.1 open item 2): *the probe counts 7 `startTextEditing` and 2
`handleTextWysiwyg` call sites. In one browser, each of P1-P8 is triggered on a note with no grant (P4
under touch emulation). P1-P4 open only after the grant. P5 is caught by the guard before any key lands
and pushes nothing. P6-P8 are unreachable (`setTool` refuses them). Non-text double-clicks still work: a
double-click on an arrow opens the linear editor, and on a group enters it; a swallowed second touchstart
is `preventDefault`ed. Pass: 8/8 paths plus 2 forwarded; 20/20 per path; 0 ops pushed before a grant.*

## Correction (2026-09-29): the guard missed editors opened while a request was pending

The first version said: "every path is intercepted, no key lands and nothing would be pushed before a
grant", and the report said the security property holds. **That was false.** Its guard ran only when
Lobby had no session (`EditorLease.onEngineChange`) or, for keys, only in the idle phase
(`CanvasInput.onKeyDown`). The spec never opened a second editor while a request was pending. The
independent verifier did, 20 of 20 times:

- Lobby's request for note A is pending (Enter or type-to-edit, grant held back or 300 ms away), and the
  user double-clicks note B's label (or selects B and clicks its label: P5). Excalidraw opens B's editor
  with `readOnly` false, and no `lease.acquire` for B is ever sent.
- Text that arrives without a keydown (`insertText`, as an IME commit, dictation or the emoji panel would
  send it) is written into B's label.
- After A's answer, Lobby's session and Excalidraw's `editingTextElement` disagree: a textarea stays in
  the document with no editing element, or an editor stays open while Lobby is idle. A's lease was
  released while A's text had not been written (it was written later, on Escape).

The new regression spec reproduces this on the unfixed code (`5203e41`, 3 repetitions per case): every
"pending A + double-click on B's label" and "pending A + P5 on B" case fails (0/3 each, with grant, manual
grant, deny and Escape). In each, B's textarea is writable (`readOnly` false) while Lobby's session is
A's, `insertText('IME')` lands in B's label (`IME` after a double-click, which selects all; `NotIMEe B`
after a click), no acquire for B is sent, the monitor records writable editors without a lease and
disagreements after every step, and in the grant cases A's text misses the keys typed after its grant.
"Pending A + type-to-edit on B" passes on both codes: the key goes to A's pending buffer, as the plan says.

### The corrected rule (`lease/openRule.ts`, pure; `lease/editorLease.ts`)

**Any editor Excalidraw has open that is not the editor of a granted Lobby lease is unrequested,
whatever the phase of Lobby's session.**

1. Its textarea is read-only from the task in which Excalidraw appended it: a MutationObserver on the
   wrapper locks every Excalidraw textarea that is not the session's own open one. Only one textarea can
   ever be writable: the one the session owns, in phase `open` (after the grant; or at once for an
   element this session created, the "New element" row).
2. `beforeinput`, `paste` and `drop` aimed at a textarea that is not writable are prevented in the
   capture phase. Excalidraw's own `onpaste` writes Excalidraw-clipboard text into the value by script
   (index.js 25303-25320), which `readOnly` alone does not stop. An `input` that still reached such a
   textarea (no path found does) is stopped before Excalidraw's `oninput` and its text put back, and the
   monitor counts it as a violation. `compositionstart` cannot be cancelled; a read-only textarea gives
   the IME nothing to type into.
3. Then: **if another request or editor is in flight** (pending, opening or open), the unrequested editor
   is closed at once with a synthetic Escape, text unchanged; keys typed afterwards go to the pending
   request, as the plan's buffer says. **If Lobby is idle**, it is re-queued as its own lease request (the
   plan's P5 guard: acquire, buffer; grant: read-only off, replay at Excalidraw's caret; deny: close
   unchanged, toast).
4. Lobby's session follows `editingTextElement` on every engine change and on every event aimed at a
   textarea: a session ends (its lease is released, or its pending request cancelled) only once its
   editor is gone, i.e. after Excalidraw's `handleSubmit` wrote the label. If Excalidraw drops a session's
   element while its textarea is still in the document (a second editor orphaned it), Lobby submits that
   textarea first, then ends the session. Before a granted open, Lobby closes any editor still left over,
   because Excalidraw keeps one submit handler and a second editor would orphan the first.

**Found while fixing:** Excalidraw's submit removes the textarea (`handleSubmit` -> `cleanup`, index.js
25487, 25543) before `onSubmit` clears `editingTextElement` (49870-49900), and the label write in between
renders. For that moment Excalidraw names an editing element with no textarea. The first draft of the rule
treated it as "the session's editor is gone and a new one opened", ended A's session and re-guarded A (a
second acquire). The regression spec caught it: every case of the first two grant tests failed (20/20 each: a
second acquire for A, and Lobby guarding an editor that was gone). The rule now waits
while Excalidraw names an element but has no textarea: nothing can be typed then.

### The regression specs (`host-a16-pending.spec.ts`)

host-lab's monitor checks, independently of EditorLease's own state: at every task boundary, no textarea
is writable unless this session holds (or created) the lease of the element it edits; no `input` event
reaches such a textarea; after every engine change (and its microtasks) Lobby's session agrees with
Excalidraw's `editingTextElement` (one textarea at most; an open editor only on the session's element;
no Lobby-open session without an editor; no writable textarea without a granted lease); every write of a
label's text happens while its lease is held; every release records the label's stored text.

## Verdict

Every path is intercepted, no key lands and nothing would be pushed before a grant, 20/20 per path in all
three runs, for one editor at a time. (The first version stopped there; the case it missed, a second
editor while a request is pending, is in "Correction" above and is fixed.) Three statements of the check do not match the engine, so the check FAILS as written; the
precise findings and corrected criteria follow.

1. **P3 on the label is not stopped by the `dblclick` listener.** A double-click on a note's LABEL opens
   the editor on the second POINTER-UP, through the P5 code (index.js 51679-51686: the note is already
   selected by the first click, so `getSelectedTextEditingContainerAtPosition` returns it), before the
   browser fires `dblclick`; `handleCanvasDoubleClick` then returns because `editingTextElement` is set
   (44727). So for the most common double-click (on the words), the editor opens BEFORE the grant, read-only
   (the guard), not "only after the grant". Double-clicks on the note body off the label, or on a note
   without a label, are stopped by the capture `dblclick` listener and open only after the grant (P3a).
   Excalidraw opens this editor with all the text selected (`initialCaretSceneCoords` is undefined after
   a double-click, 51685, so `autoSelect` runs `editable.select()`, 25613-25614); the keys buffered
   during the pending window then replace it on the grant, exactly as if the lease had been instant.
2. **A plain double-click on a simple arrow does not open the linear editor.** It falls through
   `handleCanvasDoubleClick` to `startTextEditing` (44838-44864) and edits the arrow's LABEL. Only a
   `line`, or Ctrl/Cmd+double-click on a simple arrow, toggles the linear editor (44741-44744). So the
   forwarded arrow case of open item 2 is really "Ctrl+double-click on an arrow" and "double-click on a
   line"; a plain double-click on an arrow is a text path and goes through the lease (lease id = the
   arrow).
3. **"0 local element changes before the grant" does not hold on a cold open.** Opening the editor
   re-measures the label: `handleTextWysiwyg` ends with `updateElement(element.originalText, false)`
   (49918), which re-runs the sticky-note layout / `refreshTextDimensions`, and `updateWysiwygStyle`
   writes the label's `x`/`y` (`app.scene.mutateElement(updatedTextElement, { x, y })`, 25212). When the
   stored layout differs from the browser's measurement — here, the first open on a fresh page (why the
   layouts differ there was not established: the first version said "a label laid out before Nunito
   loaded", which its own log did not show, see "The cold-open test, corrected title"); in production a
   server-made layout from the metrics table (§2.11) — the open itself writes the label (observed: `x`
   and `width`, version +1) before any key. Those writes are the leased label's `layout`
   group, which the guard holds back (§2.9.2 guard step 3), so nothing would be pushed. The 20-case
   loops warm the font first (0 changes in all cases); a separate cold-open test records the re-layout
   and asserts that every change is held back.

**Proposed corrected criteria:** *"P1, P2, P3 off the label, P4 and Lobby's T tool open only after the
grant. P3 on the label and P5 are caught by the guard: the textarea is read-only from its first frame,
no key lands before the grant, and nothing is pushed (every local change before the grant is the leased
label's text/layout or its container's fit). P6-P8 are unreachable. Forwarded: a double-click on a
`line` and Ctrl/Cmd+double-click on an arrow open the linear editor; a double-click on a selected group
enters it; a plain double-click on an arrow edits its label through the lease."* Against these, A16
passes 3/3.

## Other engine behaviour found

- **The call-site probe holds:** `startTextEditing` has 7 call sites (`this.` x6 + `app.` x1 in AppToolDrag
  at 27824) and `handleTextWysiwyg` 2 (44685, 51250), in `dist/dev` and in the minified `dist/prod` (the
  method names survive minification).
- **Touch double-tap never reaches the linear-editor or group branches.** `onTouchStart` calls
  `this.deselectElements()` before `handleCanvasDoubleClick` (43506-43516), so on touch the double-tap is
  always a text path (or an embed): Lobby can swallow every one-finger second tap within 300 ms / 35 px.
- **Excalidraw's own touch double-tap is racy off iOS.** It calls `preventDefault` on touchstart only
  `if (isIOS)` (43481-43483). Elsewhere, the second tap's compatibility `mousedown` arrives 1-2 ms after
  `touchend` and moves the focus from the just-opened textarea to the container (observed in a
  separate 12-case probe, every time: `focusout TEXTAREA` / `focusin DIV.excalidraw`, then the textarea
  re-focused). In the `dbl=off` control, 1 of the 5 editors closed again at once in each run (the guard
  logged `closed-while-pending`). That is consistent with bindBlurEvent's `setTimeout` (25545-25561)
  having armed `onblur = handleSubmit` before the mousedown in that case; the spike did not trace the
  close step by step. Lobby's
  `preventDefault` on the swallowed touchstart suppresses the compatibility mouse events for that tap, so
  Lobby's path is not racy. **Plan correction:** Lobby calls `preventDefault` on the swallowed touchstart
  on every platform, not only on iOS.
- **P5 keeps the click caret.** A single second click opens with `initialCaretSceneCoords` = the click
  point (51685), so the replay inserts at that caret (`Lab|el 0` -> `Labzqel 0`).
- **P4 needs `stopPropagation` in the capture phase with `passive: false`.** Excalidraw's listener is a
  native `touchstart` on the interactive canvas (47143-47148), not React; a capture listener on the
  wrapper stops it before the target phase.

## Deviations from the plan

- Pass criteria: see Verdict and the proposed corrected criteria.
- "Pushes" are measured as local element changes (version or nonce) and, for the cold open, as changes
  outside the guard's held-back set; spike A has no sync engine to count real ops.
- The forwarded arrow case uses Ctrl+double-click (finding 2); a plain arrow double-click is tested as a
  text path.
- **Plan correction, §2.9.2 "The guard"**: "every editor open that did not follow a grant" must read
  *"every editor Excalidraw has open that is not the editor of a granted lease, whatever the state of
  Lobby's own request"*, and the steps need two more: *"while another request or editor is in flight, the
  unrequested editor is closed at once, unchanged (keys typed afterwards go to the pending request); text
  that arrives without a keydown (beforeinput, paste, drop) is prevented, not only keys"*, and *"Lobby's
  session follows editingTextElement; the lease is released only after the editor is gone (its text
  written)"*.
