### How the pass reaches the engine's render (no spike-owned edit)

Excalidraw 0.18.0-1118751 has one render-only knob per element: the render-override snapshot
(`setElementRenderOverrides`, `types.d.ts` 1095-1110; exports and interactive geometry keep document
values). Its renderer culls an element whose render offset moves it out of view
(`Renderer.getVisibleElementsWithRenderOffsets`, `dist/dev/index.js` 24150-24205). Opacity 0 does not
help: the element is still drawn, invisibly (measured, §3).

`canvas/overrides.ts` (spike B) owns that snapshot (`RenderOverrides` merges drag previews and mind-map
collapses and submits them to the API it was given). The board page now gives `installBoardOverrides`
the API through `createLodTarget` (`canvas/lod/cull.ts`): a Proxy that forwards everything, whose
`setElementRenderOverrides` adds the pass's culled ids to each snapshot `RenderOverrides` submits (an id
the snapshot names keeps its entry) and re-submits that merge when the culled set changes.
`RenderOverrides`' own state (`isHidden`, `blockReason`, the hit guard, the selection filter) never sees
the culled ids. CR 3b-5 asks spike B to own this merge in `RenderOverrides`.

The bitmaps are Lobby's own frame export (`canvas/export/scene.ts` `exportSceneCanvas` with `frameId`:
the frame's members clipped to it, no outline or title, `files: 'canvas'`, transparent, the board's
theme), at 0.2 × the device pixel ratio (at most 2,048 px a side), kept as ImageBitmaps. The layer is one
`<canvas data-lobby-lod>` right after Excalidraw's static canvas (above the static scene, which still
draws the frames' outlines and names and every loose element; below the interactive canvas: selection,
handles, hover). A pan draws copies made at the settled scale (`createImageBitmap` with a resize, off the
main thread); a zoom in progress draws the originals scaled.

## 2. Deviations from today's behaviour

1. **Only frames are cached.** Loose elements (outside any frame) are always drawn by the engine, as the
   plan says ("a cached bitmap per frame"). A heavy board of loose notes gains nothing below 0.2.
2. **A zoomed-out frame is a picture of its contents at 0.2.** Below 0.2 notes are 40 px or less and their
   words are not readable in either engine; the bitmap is Excalidraw's own export of the frame, so what it
   shows is what the engine would draw. The eraser's "about to erase" fade is not shown on a culled
   element (it is drawn by the static render, which leaves culled elements out).
3. **The zoom wheel below 0.1 steps 10% of the zoom per notch** (a ratio); Excalidraw's own wheel steps
   0.1 of zoom per notch, which below 0.1 would be a jump to 0.
4. **Touch-screen pinch still stops at 0.1.** A two-finger pinch on a touch screen is Excalidraw's own
   pointer gesture, and Lobby's input stream has no pinch event for it (`pinch` there is the trackpad's
   Ctrl + wheel). The zoom menu, the keys and Zoom to fit go below 0.1 on a phone too.
5. **The keys from the chrome include Ctrl/Cmd+Shift+= and -** (tldraw's zoom-on-cursor), which the key
   allowlist otherwise delegated to Excalidraw's own zoom (the keyboard-map test lists both, with why).

## 3. Measurements (the §8.5 gate: ≥ 24 fps at Lobby's whole-board fit)

Method: `e2e/excalidraw/navigation-lod-fps.spec.ts` (opt-in, `LOBBY_MEASURE_FPS=1`), spike A14's and spike
B's method: the heavy board (20 frames, 4,500 notes with labels, 200 uploaded images, 40 threads: 9,220
elements) seeded through the real protocol, opened through the real stack in Playwright's headless shell
with GPU flags (ANGLE D3D11, RTX 5090, `2d_canvas` enabled), 1536 × 864 at DPR 1.25, the pointer at rest,
nothing selected, 3 scripted pans of 3 s per view (a 600 px sine) plus one traced pan; the camera moves
through `LobbyCanvas.viewport.set`. Views: Lobby's whole-board fit (zoom 0.0455), 0.25 and 1 on frame 0.
Each mode is measured in the same page and the same machine state.

**Not a quiet window**: other agents' stacks and browsers ran on the workstation throughout (the
"machine" column is the whole-machine CPU share during the pans). Cells: the median of a run's 3 pans
(then the 3 pans); for three runs, the run medians and the median of them.

| Tree | Mode | fit (0.0455) | 0.25 | 1 | machine busy |
|---|---|---|---|---|---|
| 1809cf3 (before) + the spec | the page as it was | **9.6** (9.6 / 10.2 / 9.5) | 25.5 (24.4 / 25.5 / 27.2) | 32 (31.3 / 32.3 / 32) | 23-27% |
| final tree (`076c38d`), 3 runs | pass off (`__lobbyLod.setEnabled(false)`) | 9.8 (9.7 / 10.4 / 9.8) | 29.5 (27 / 29.5 / 31.3) | 35.5 (34.6 / 35.5 / 36.5) | 10-18% |
| final tree (`076c38d`), 3 runs | **pass on** (the default) | **28.2** (25.2 / 32.5 / 28.2; the slowest single pan 25.1) | 31.5 (30.2 / 31.5 / 32; the pass is off at 0.25) | 35.8 (34.3 / 35.9 / 35.8) | 8-17% |

Every pan with the pass on was at or above 24 fps at fit, against 9.5-10.6 with it off in the same page.
With the pass on the 20 bitmaps took 275-358 ms to render in total (14-18 ms each) and were ready within
the 2.5 s the spec waits after the camera move. The main thread is 99.9% busy in every traced pan, at
every view. An earlier run of the pass (before the bitmaps became ImageBitmaps drawn from copies at the
settled scale) measured 25.9 at fit; its CPU profile put the paint of 20 downscaled canvases at about
6.5 ms of main thread per frame, which the copies remove.

**Probes** (the readable build, one CPU-profiled pan each; the elements' render changed straight on the
engine's snapshot, no bitmap drawn): every frame child at **opacity 0: 7.7 fps** at fit (123 ms busy per
frame); every frame child **culled by a far render offset: 34 fps** at fit (29.4 ms per frame); zoom 1
with nothing changed: 35 fps (28 ms per frame). So the culled fit costs what zoom 1 costs, and opacity is
not a way to skip the render.

**Where the rest goes** (the profile at zoom 1, 28 ms busy per frame, the pass not involved): spike B's
engine core scans the scene on every camera move (Excalidraw calls `onChange` for scroll changes:
`record`, `scanNow`, `sceneMap`, `sync`, the port's `afterSceneChange` version scan: about 15-20%), and
Excalidraw's own per-frame `getVisibleCanvasElements` / `getRenderableElementsMap` over all 9,220 elements
(about 8%), plus the React render of the engine. This is why 0.25 and 1 stay near 30 and 36 fps, at or
just below §8.5's 30 fps at 0.25 depending on the machine's load: CR 3b-8 (§4). The pass cannot change it
(it is off at 0.25).

**Open** (informational, the same spec): the heavy board opened in 12.9 s on 1809cf3 (one run) and in
4.3-4.5 s on the final tree (three runs; from navigation to "every element on the page and Saved"); the
likely cause is the first view's content bounds, which were quadratic. Not profiled.

## 4. Change requests

**Applied (`CR:` commits):**
- **CR 3b-2** (`canvas/api/lobby-canvas.ts`, 2C's `canvas/board/input.ts`): the `wheel` and `pinch` input
  events carry `deltaX`, `deltaY`, `deltaMode` (optional, additive). For the contracts owner's §12.
- **CR 3b-6** (`canvas/api/impl.ts`, one line): `viewport.fit` comes from 3b's part (the member table is
  unchanged: `viewport.fit` stays core, delegated; lobby-canvas.ts already names 3b for the sub-0.1 fit).

**Requested (spike-owned files, not edited):**
- **CR 3b-5 (spike B, O5, `canvas/overrides.ts`): a render-only cull source in `RenderOverrides`.**
  `setCulled(source: string, ids: Iterable<string> | null)`: the ids get `{ offset: LOD_CULL_OFFSET }`
  (1e9, 1e9) in the merged snapshot unless a drag preview or a collapse already names them (theirs win), and
  never count in `isHidden`, `blockReason`, `movingSource` or `hiddenIds`. Plus a way to read who moves what
  (`movingSource` exists) and a change callback (or the pass keeps its own reading of the snapshot). Then
  `canvas/lod/cull.ts`'s Proxy goes: `session.ts` passes `api` again, and the pass calls
  `overrides.setCulled('lod', ids)` through `overridesOf(registries)`. Test: a culled id stays hittable
  (the guard's `isBlocked` false), selectable, and is dropped from the snapshot when the source clears.
- **CR 3b-7 (spike B, O2, `canvas/port-impl.ts`): O(1) `get` and `bounds`.** `byId` is
  `all().find(...)` and `bounds(id)` builds `new Map(all())` per call (port-impl.ts 95-96, 199-205): use
  `api.getSceneElementsMapIncludingDeleted()` (exported, `types.d.ts` 1085) for both. Every feature loop
  that calls `canvas.bounds(id)` or `canvas.get(id)` per element is quadratic on the heavy board (3b's
  are now one-pass; others remain: search boxes, `visibleBounds`, `boundsOf`, 2C's `fitTarget`, the
  board page's hit tests). Spike B's PERF.md found the same (`bounds` per image per camera move).
- **CR 3b-8 (spike B, O2, `canvas/sync/adapter`, the core, `port-impl.ts` `afterSceneChange`): no element
  scan on a camera-only `onChange`.** Excalidraw calls `onChange` for every appState change, a pan's
  scroll included; the core scans the scene and the port compares all versions each time (15-20% of the
  main thread at every zoom on the heavy board). Skip both when the scene's element array (or
  `getSceneVersion`) is unchanged. This is what keeps 0.25 below §8.5's 30 fps.
- **CR 3b-9 (spike B, O2, `port-impl.ts` `viewport.set`; 2C's `CameraTween`): `shouldCacheIgnoreZoom`
  during a continuous zoom.** Found in the code, not measured: Excalidraw regenerates a visible element's
  canvas cache whenever the zoom differs from the one it was drawn at, unless `shouldCacheIgnoreZoom`
  (`@excalidraw/element` `generateElementWithCanvas`, dist/dev/index.js 13809-13815); its own wheel sets it
  during a zoom and clears it 300 ms later (`AppWheel.zoomBy`, dist/dev/index.js 29497-29536; the debounce at 47807). Lobby's
  `viewport.set` never does, so every frame of an animated zoom (the tween, Lobby's wheel below 0.1)
  regenerates every visible element's cache. Below 0.2 the pass culls the framed ones; above it, it does
  not. Suggest `viewport.set(v, { continuous: true })` (or the tween's own flag) setting it and a
  debounced clear.
- **Test facade (O3, `canvas/test-facade.ts`):** `zoomToFit` and `fit` use the port's fit (0.1 floor);
  specs that want Lobby's fit call `__lobbyBoard.canvas.viewport.fit()`. Optional.
- **Touch pinch below 0.1 (2C / spike B input):** would need a two-pointer pinch event in the input stream
  (deviation 4). Not requested unless the owner wants it.

**Findings in other owners' code** (not fixed here):
- **3a, `ShortcutsDialog.tsx`:** closing the dialog calls `canvas.focus()` while the modal `<dialog>` is
  still open (the rest of the page is inert), then React removes the dialog; the focus sometimes ends on
  `<body>`, where "?" and Ctrl+/ reach no key handler (the command is canvas-scope). `a11y-3` "?" and
  Ctrl+/ open the shortcuts" is flaky for it, on 1809cf3 too. Fix: focus after the dialog is closed (or
  `d.close()` first), and consider the shortcuts key from the chrome (the tldraw page's
  `CHROME_SAFE_ACTIONS` has it; 3b's chrome keys cover only the camera and search).
- **3f, `workshops-private-notes`:** the api's per-user brainstorm-start limit ("That is a lot of
  brainstorms") trips when the file runs fast: one test fails every run of the file on 1809cf3 and here.
