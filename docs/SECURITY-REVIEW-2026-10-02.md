# Security review addendum — 2026-10-02 (wave A, workstream A6)

This addendum follows [SECURITY-REVIEW-2026-09-27.md](SECURITY-REVIEW-2026-09-27.md). It closes the items that review left open ("Review the M3 storage work once it is committed", "Dependency vulnerability scanning", and the three optional hardening notes SCA-3, CSD-4 and FC-3), and it closes two audit items found since (GUEST-JOIN-TRASH, AUDIT-INTERNAL-SCOPE). It was done on a branch taken from `49b711d` (main, after the Excalidraw cut-over). Nothing here touches the live staging site, Render, Clerk, R2 or the NAS: the review read code and ran local tests, and the dependency scan is the one command that talked to the npm registry.

**Result.** No finding gives an unauthenticated caller access to data, and none crosses tenants. Six small hardening changes were made, each with a test that fails on `49b711d` and passes with the fix. The dependency scan found 12 advisories in the production tree, all inside `@excalidraw/excalidraw`'s own pinned dependencies in `apps/web`, none reachable from Lobby's use of them; two exact-pinned overrides remove 7, and 5 remain (a major-version bump and a package with no patched release), recorded below for the owner. The M3 storage code (worker routes, blob store, R2 keys, signed URLs, limits) is in good shape: no exploitable defect, one fail-open default fixed, and four observations for the owner.

## 3. M3 storage review (worker, blob store, R2, signed URLs, limits)

**Scope.** Read-only, plus the one fix above. `apps/api/src/worker/*` (auth, protocol, jobs, routes, fs-mode blob URLs), `apps/api/src/files/*` (upload, receive, serve, range, disposition, mime, meta, usage, GC and its report routes, storage config), `apps/api/src/files-auth.ts`, `packages/blob-store/src/*` (keys, the fs store, the R2 store, argument checks), and `apps/worker/src/*` (the API client, transfers, sniffing, sharp, the PDF child, ffmpeg, the Office sidecar and its ZIP guard, the process runner, environment loading).

### 3.1 Checked and OK

- **Worker authentication.** `Authorization: Bearer` compared in constant time (both sides hashed first), a Cookie header is refused outright (403), the routes are exempt from the Origin check only by matched pattern, and rate limits are per token or per address without a valid one (6,000 and 600 per minute). `DRAFTROOM_WORKER_TOKEN` must be at least 32 characters, is not a `dev-only-` value in production, and must differ from the ticket and internal secrets (`config.ts`). Tests cover wrong, missing and cookie-carrying requests.
- **Claim, heartbeat, reserve, complete, retry.** Every lease-bound call re-checks `status = running`, the lease owner and the attempt under a row lock. A reservation can only be listed by the attempt that made it, its blob must exist with exactly the reserved size and type before `complete` publishes it, probe facts are re-sanitised, an unknown failure code becomes the generic user-safe message, and a job gives up after 3 attempts with backoff. The worker's own text is never shown to users.
- **fs-mode blob URLs.** `kind.id.expiry.mac` (HMAC-SHA256, 132 bits, under a key derived from the worker token, so rotating the token revokes every URL): one blob, one method, 900 seconds. A GET works only while the job is running; a PUT only for a live reservation of the current attempt, with `Content-Length` and `Content-Type` equal to the reservation, streamed with a hard byte cap.
- **R2 keys.** Built only from validated ids (`ast_`, `ver_`, `drv_` plus a fixed extension), then checked again by the store: segments of `[A-Za-z0-9_.-]`, no empty or dot-leading segment, no Windows device names, 512 characters at most. The fs store also resolves and checks the path stays under its root, writes atomically, and never follows a key into a directory. Nothing request-derived reaches a key.
- **Signed URLs.** Only the worker ever receives one (`presign*` is used nowhere else in the api, sync or web). Both kinds live 900 seconds, the store's maximum, enforced by `checkExpires`. A presigned PUT signs `Content-Type` and `Content-Length`, so R2 enforces the reserved size. No signed URL is stored in a record or logged (the worker's own rule is the same: it never logs a URL). The worker adds its bearer token only for the API's own origin, uses `redirect: 'error'` on every request, and rejects blob URLs with credentials or a non-http(s) scheme.
- **Serving.** Authorization comes first and a miss is the same 404 as a missing asset. Originals are inline only for allowlisted types of the previewable kinds (PNG, JPEG, WebP, GIF, PDF, MP4, QuickTime, WebM) and otherwise an attachment; every response has `nosniff` and `Content-Security-Policy: sandbox; default-src 'none'`; `Content-Disposition` is escaped (ASCII fallback plus RFC 5987); derivatives are served only once `complete` has published them; originals are stored as `application/octet-stream`. Range requests handle one range and ignore the rest.
- **Upload.** The caller needs `edit` on an active board before any header is read; then a per-user rate limit (120 a minute), `Content-Length` required, a per-kind byte cap (image 25 MiB, PDF and Office 100 MiB, video 500 MiB, other 250 MiB), the workspace quota (2 GB, 5,000 files) and a guest allowance, checked again under a workspace row lock with the real size, and a streaming meter that stops at the declared size. Partial blobs are deleted on any failure.
- **Worker processing limits.** Images: loader allowlist (JPEG, PNG, WebP, GIF only; SVG, PDF, TIFF and HEIF blocked in libvips), 100 megapixels, first frame only, 20 second timeout, 2 threads. PDFs: a separate Node process with a heap cap (384 MB) and a SIGKILL timeout (90 seconds), at most 2,000 pages and 8 rendered, output edge at most 4,096 px, its output re-validated by the parent. Video: ffprobe and ffmpeg with the MP4 demuxer forced, only the `file` protocol, external references off, H.264 and AAC only, at most 3840 by 2160 and 15 minutes, bounded stdout. Office: a ZIP structure and zip-bomb check before conversion (10,000 entries, 1 GiB declared, entries inflated against their declared size, macros and encryption refused), then LibreOffice in a sidecar with no network and no secrets, paths confined to the shared jobs directory. Every child gets an environment of `PATH` only (`run.ts`), so none of them can read the worker token.
- **Worker configuration.** Refuses `http` API URLs outside a private network in production, refuses an unknown `NODE_ENV`, and names (never prints) any credential present that the worker does not use.
- **SQL.** The only interpolations in these files are fixed column lists; every value is a parameter.

### 3.2 Findings

| ID | Severity | Finding | Status |
|---|---|---|---|
| M3-1 | Low | The worker routes were fail-open: with no `@fastify/rate-limit` registered before the plugin, the limiter was skipped silently. Registration order is correct today (`app.ts`), so this was latent. | **Fixed** (`3c1ae0b`). |
| M3-2 | Informational | One shared worker token is a master key for previews: whoever holds it can claim any job, read every original through the presigned URL it is handed, and publish any derivative. This is the design (workers hold no database or R2 credentials), and the controls above bound what a non-holder can do. | For the owner: keep the token out of the browser-facing env groups, rotate it if a worker host is lost (rotating also revokes every fs-mode URL), and consider an IP allowlist at the Render edge for `/api/worker/*`, which is reachable on the public API origin. |
| M3-3 | Informational | The API sets no request or body timeout (Fastify's `requestTimeout` is 0, measured on 5.12.5; `headersTimeout` is 60 s). Uploads to R2 have a 60 second stall timer, but a JSON route's slow body, or an fs-store upload, can hold a socket as long as the client likes. | Not changed. A value must clear the slowest legitimate 500 MB video upload, and what Render's edge already enforces cannot be checked offline. For the owner: pick `requestTimeout` (for example 60 minutes) once the edge behaviour is known. |
| M3-4 | Informational | Presigned URLs live 900 seconds. A signature only needs to be valid when a request starts, so 300 seconds would do for the worker's flow and shrink the window for a leaked URL. | Not changed: 900 is the documented contract maximum and the saving is small. |
| M3-5 | Informational | `GET /files/...` has no rate limit of its own (each call is one session lookup, one board-access query and one version query). | Not changed; a global per-user read limit is a product decision. |
| M3-6 | Informational | pdf.js `isEvalSupported` was not a concern: the option no longer exists in the installed pdfjs-dist 6.3.289 (checked in its types and `legacy` build). | None needed. |

### 3.3 Not covered

- **The live R2 bucket and its policy** (public access, CORS, lifecycle, token scope): needs the Cloudflare account. The separate least-privilege backup bucket is already an owner item.
- **Real R2 and real Clerk behaviour.** `r2-live.test.ts` and the Clerk exchange stay unrun here (no keys); SCA-3's absent-`sts` case in particular is decided from `@clerk/backend`'s source, not from a live token.
- **Edge behaviour on Render** (timeouts, the real `X-Forwarded-For` chain).
- **Fuzzing the decoders.** The limits above were read and their tests inspected; no hostile corpus was run through sharp, pdf.js, ffmpeg or LibreOffice in this pass.
- **The sync server's file-ref and asset-ref handling**, which belongs to the Excalidraw room review.
